# Master Farmer - Grindbot versioning

Copy-forward. Never rename or delete an old version folder.

## Identity

Canonical fields live in `version.lua`. `header.lua`, the GUI title, and the load log must match that table.

## On a material change

1. Copy `Master_Farmer_Grindbot_vX.Y.Z` to `Master_Farmer_Grindbot_vX.Y.(Z+1)` (or the next semver).
2. Edit **only the new folder**.
3. Update `version.lua`, every `-- Version:` / `-- Folder:` banner, GUI version text, and the load log.
4. Point the Cursor workspace at the new folder.
5. Do not bump for comment-only or rule-only edits.

## Revert

Disable the newer plugin in Sylvanas and enable the older `Master_Farmer_Grindbot_vX.Y.Z` folder.

Added the class weapon-proficiency and numeric armour tables that make "usable" mean something - a Mage no longer takes the plate chest because it sells for more. New `mfg_quest_debug` logs every step and every choice considered. |

| 1.7.0 | Memory. Measured, not guessed: **2,281 KB resident before, 1,559 KB after - 722 KB / 32% less** with the plugin installed and one grind route loaded. Three changes. (3) `leveling_paths.lua` and `data/_zones_raw.lua` are unreachable from `main.lua` (verified by transitive trace) and `_zones_raw` was the only thing pulling all four race zone tables at once, so both are excluded from the manifest. | 1.9.2 | Game Events audit. The project never called `core.register_on_game_event_callback` at all, and of the four confirmations the client **holds open until answered**, only the equip pair was being handled - by polling the latched `core.game_ui.get_pending_equip_slot()`, which the documentation explicitly blesses. **`LOOT_BIND_CONFIRM` was unanswered, and there is no latched reader for it**: the event is the only place the loot slot number exists. So every bind-on-pickup drop was left on the corpse while `loot.lua` burned its three attempts and gave up - on a levelling grind bot, precisely the loot worth having. New `events.lua` registers one callback using the documented handler-table dispatch and answers `LOOT_BIND_CONFIRM` with the **1-based to 0-based conversion** the docs warn about twice (forwarding `args[1]` straight through confirms the slot *after* the one that asked), plus both equip confirms on the edge and `CONFIRM_BINDER` so it can never hang. Registration is guarded on `_G.MasterFarmer_Grindbot`, not a module local: the callback cap is per plugin and this plugin hot-reloads by clearing `package.loaded`, so a module-local guard would re-register on every reload until the cap raised a Lua error. The handler table is re-read through the namespace, so a reload still runs new handler code through the original callback. The cast, aura and combat-log families are deliberately **not** registered - the documentation is explicit that a rotation should poll `game_object` for what a unit is casting, which every rotation here already does. |

| 2.0.1 | **The running plugin was v1.3.38 the whole time.** `plugin_loader/main.lua` held a hardcoded commit SHA, and it had never been re-uploaded - so the loader kept fetching a commit 29 behind while every new version sat in the repository unseen. Every "nothing has changed" in this session was that. The loader now resolves the branch head itself: one request to `api.github.com/repos/<repo>/commits/<branch>` with `Accept: application/vnd.github.sha`, which answers with the bare 40-character commit id, and every file is then fetched from that immutable commit URL.
